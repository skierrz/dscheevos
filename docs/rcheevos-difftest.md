# rcheevos differential test harness: spec

Status: spec, 2026-10-12, for eval-speed to build once. Every rcheevos patch must pass it, starting with the two on the way: the partition split (ARM9 + ARM7) and change-driven evaluation. It makes `docs/compliance.md` "Evaluating one set on two CPUs" §4 executable. The rule it enforces (CLAUDE.md): a patch is allowed only where its evaluation results are proven identical to stock rcheevos on every real set with real RAM, kept minimal, and offered upstream.

## Shape

Two programs. Two copies of rcheevos can't be linked into one process (their symbols clash), so each build runs in its own process and the logs are compared.

- **`difftest-run`**: runs one rc_client over a trace and writes a canonical log. One binary per rcheevos build:
  - `difftest-run-stock`: the pinned upstream commit, no patches;
  - `difftest-run-patched`: our fork's pin.
  - Options: `--set FILE` (an `achievementsets` reply), `--session FILE` (a `startsession` reply), `--trace FILE`, `--script FILE` (lifecycle), `--mode single|partition`, `--split SPEC` (partition only), `--features LIST` (which patch features are on; empty = inert), `--hardcore 0|1`.
- **`difftest-cmp A.log B.log`**: exit 0 if identical. Otherwise it prints the first differing frame, both sides' records for that frame, and the 10 frames before it.

Same source for both binaries apart from the rcheevos tree; `tests/difftest/` in the repo.

## Inputs

**Sets:** every real set we have (`private/sets/sets-*.json`, the server's `achievementsets` replies, 32 today), plus the public synthetic sets in `tests/` so CI has something to run.

**Session replies:** per set, at least two `startsession` replies: one with no unlocks, and one with about half the achievements unlocked (some in hardcore, some in casual only), so loads with earlier unlocks are covered. Generated by the harness from the set's IDs in the server's reply format, and kept private with the sets.

**Traces** (rnd produces the real ones):
- Format: a base image of main RAM (4 MB; 16 MB for DSi-mode games) and DTCM (16 KB), then one record per frame: the frame number, flags (`LAG`: the module would evaluate this VBlank as a repeat; `MENU`: the game is stopped), and the byte ranges that changed since the previous frame. The read callback serves bytes from the reconstructed frame, exactly as the module serves them from its snapshot. Real traces may instead be **read sets**: every (address, size, bytes) rcheevos read that frame, as rnd's logger records them. Then a read that isn't in the recording fails the run, since it means the candidate reads differently.
- **Real:** at least 10,000 consecutive frames per set, from real play of that game with the idle-budget input scripts and real RAM dumps. Kept private.
- **Fuzzed:** at least 100,000 frames per set, generated from the real trace with a fixed seed, which goes in the log header. The mutators work on the set's watched addresses, including pointer-chain targets resolved on the frame:
  - random byte or word changes;
  - sweeps through each condition's constants (value - 1, value, value + 1);
  - freezes: memory held unchanged for 1 to 600 frames;
  - toggles (A, B, A, B);
  - pointer moves (a chain base changes, then its target);
  - addresses near the end of a region (short reads).

## Fake server and clock

- `server_call` answers from the set and session files: `login2` with a fixed token; any award, submit or ping with success. Every request is logged.
- A script can make the next N requests of a kind fail (`FAIL award 3`), which exercises rc_client's retry and queue paths.
- Clock: `rc_client_set_get_time_millisecs_function` with a fake clock that advances 1001/60 ms per frame. Pings, retries and anything time-based then land on the same frame on both sides. Anything else that reads the wall clock is pinned to a fixed epoch.

## Lifecycle script

Lines of `FRAME COMMAND [ARGS]`, run before that frame's `rc_client_do_frame`:

| Command | What it does |
|---|---|
| `LOAD` / `UNLOAD` | `rc_client_begin_load_game` (through the fake server) / `rc_client_unload_game` |
| `RESET` | `rc_client_reset` |
| `HARDCORE 0` | `rc_client_set_hardcore_enabled(client, 0)` (never 0 to 1 mid-session, as B forbids) |
| `PAUSE N` | no `do_frame` for N frames, only `rc_client_idle` each frame (the in-game menu: the game is stopped) |
| `SHORTREAD ADDR LEN N` | the read callback returns short for that range for N frames (rc_client then disables what reads it) |
| `FAIL KIND N` | the fake server fails the next N requests of KIND |

Every set runs with these scripts:
1. a clean run;
2. resets at 5 random frames;
3. hardcore to casual at a random frame;
4. 3 pauses of 600 frames;
5. one short read on a watched address;
6. award failures followed by success;
7. unload and reload mid-trace.

Each script runs with both session replies.

## What is logged and compared, every frame

One record per frame f, written after frame f's `rc_client_do_frame` (or `rc_client_idle` while paused):

1. **Events**: every event rc_client's handler received during that call, in the order received. For each: the type, the achievement or leaderboard ID, every payload field byte for byte (title and description pointers resolved to their text, state, `measured_progress`, `measured_percent`, the leaderboard tracker's display and value, the submitted score, game completed). This gives the timing to the frame: an event that moves to another frame fails.
2. **State**: for every achievement, its id, state, bucket, unlocked flags, unlock times (from the fake clock), `measured_progress` and `measured_percent`. For every leaderboard, its id, state and tracker value. The rich-presence string (`rc_client_get_rich_presence_message`). The user game summary. **And the bytes of `rc_client_serialize_progress`**: every memref value, prior and changed flag, and every condition's hit count. That catches a state difference before it ever causes an event.
   - To keep logs small, the record holds the SHA-256 of this block. On the first mismatch, `difftest-cmp` reruns both sides to that frame with the full text.
3. **Requests**: every server request issued during that call: the API name and post data, byte for byte.

The log header records the rcheevos commits, the set file hash, the trace hash and seed, the script, the mode, the split and the features. `difftest-cmp` refuses to compare logs whose inputs differ.

## Runs and pass criteria

For each patch, every set, every trace (real and fuzzed), every lifecycle script, both session replies, and hardcore on and off:

| Run | Compared with | Must be |
|---|---|---|
| patched, all features off | stock | identical: the patch is inert |
| patched, each feature on alone | stock | identical |
| patched, all features on | stock | identical |
| partition patch: production split, and 20 random splits per set (seeded) | stock | identical |
| rcheevos' own test suite on the patched tree | - | passes |

**Pass = zero differences in every comparison.** One differing byte in one frame of one run fails the patch. There is no tolerance and no allow-list.

## Patch-specific stressors

Built into the fuzzed traces, and listed in the report:
- **Change-driven evaluation** (skipping work when watched memory didn't change):
  - freezes of 1 to 600 frames while conditions with hit targets are true (hits keep counting on frames with no change);
  - delta and prior values across a freeze;
  - `LAG` frames and the module's repeats;
  - measured values that change without a memory change (hit-count measured);
  - a reset or a hardcore switch during a freeze;
  - pause and resume.
  eval-speed: confirm the patch's shape, so this list can name its exact skip condition.
- **Change-driven evaluation, as eval-speed defines it** (`evalspeed-team/change-driven.md`). S0 skips trigger T at frame f when every memref T reads (direct, modified and indirect) had `changed == 0` at f and at f-1, and T's evaluation at f-1 wrote no state and returned `T->state`. S1 also adds +1 to "plain tally" conditions on the skipped frame. Stressors:
  - delta and prior values right after a change (changed at f-1 only);
  - a pointer that changes while its target doesn't, and the reverse;
  - triggers in WAITING, PRIMED and PAUSED;
  - ResetIf and PauseIf with hit targets;
  - AddHits and SubHits totals approaching a target;
  - Measured and MeasuredIf (progress events), and `measured_as_percent`;
  - leaderboards and rich presence sharing memrefs with skipped triggers;
  - unlock, reset and reactivation (`rc_client_reset`, the hardcore toggle) clearing the skip flags;
  - memref changed flags across a game reset;
  - long freezes (our repeats and lag frames);
  - for S1, hit tallies at their arithmetic limit.
- **Partition split:**
  - the external evaluation path is given no read function and must make no read;
  - the ARM7's work list is exactly the triggers rc_client evaluates that frame (never an inactive or unlocked one);
  - frame f+1's memref update starts only after the ARM7 finishes f;
  - achievements and leaderboards whose memrefs live on both sides;
  - rich presence sharing memrefs with remote achievements;
  - leaderboards whose start, cancel and submit fall in one frame alongside remote unlocks;
  - mastery reached by a remote unlock;
  - short reads on a remote-only memref.

## Where it runs

- **Host CI** (public, every push that touches the rcheevos pin, `dscheevos/core` or `tests/difftest`): x86-64 Linux, plus armv7 in docker (`--platform linux/arm/v7`, as the memplan harness does) for the 32-bit ARM ABI and float behaviour. The partition runs also go once with the remote triggers evaluated in a second thread, concurrently and in reverse order, under ThreadSanitizer: the two sides write disjoint memory, so order must not matter. Inputs: the public synthetic sets and homebrew traces only, because real sets and RAM are private. About 3 sets x (10,000 + 10,000 fuzzed frames) x every script: minutes, not hours.
- **Full corpus** (local, before every merge of a patch or a pin change): every real set and trace, both architectures, through `build-lock`. It also runs **the real devkitARM builds** (armv5te with the module's flags for the ARM9 side, armv4t for the ARM7's trigger evaluation) under qemu-arm user mode, which proves the cross-ISA claim on the production compiler. The run writes `tests/difftest/REPORT.md`, which is committed. It holds no private data: the set IDs, the hashes of the traces and replies, the seeds, run counts, zero differences, the rcheevos commits and tool versions. The merge request cites it.
- **Console build** (before a patch first ships, and after any compiler change): run the DScheevos module in melonDS with a trace-export option. Per frame, it writes the snapshot the module evaluated and the module's event log, at least 10,000 frames each for Kirby Super Star Ultra, Mario Kart DS and one heavy set. A host replay of stock rcheevos over the exported snapshots must give the same event log. This catches devkitARM and armv4t/armv5te differences.
- **On a DSi:** the same module build is a smoke test only (the events look sane, nothing crashes). Per-frame snapshots can't be exported from hardware: no SD writes during play. State this limit in the report rather than imply hardware equivalence.

## Out of scope

Performance, memory use and the game-cost evidence: separate gates, in `tests/perf` and COMMON.md "Game-cost evidence".
